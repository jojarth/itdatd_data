# Site Reference

This page documents the site-specific tools used while writing ITD&TD pages.

Keep this page in `src/content/docs`. Starlight only treats files in the docs collection as normal documentation pages with the site layout, sidebar, search, table of contents, and routing. If this moved outside `docs`, it would need a custom page route and would stop behaving like the rest of the manual.

## Reusable Blocks

Use reusable Astro components when the same rules text, card, or table needs to appear in more than one place. This avoids copy/pasting and lets one edit update every reference.

Reusable blocks live in `src/components/reusable/`.

Example import:

```mdx
import KeywordFeatureCard from '../../../../components/reusable/KeywordFeatureCard.astro';
```

Example usage:

```mdx
<KeywordFeatureCard toc />
```

Props let reusable blocks vary the class-specific parts of the text.

```mdx
import OrderFeatureCard from '../../../../components/reusable/OrderFeatureCard.astro';

<OrderFeatureCard
  className="Cleric"
  traditions={['Military', 'Devotional', 'Stewardship']}
  toc
/>
```

Reusable blocks should render the exact markup they mean to insert. For example, use `<p>` tags for paragraphs inside `.astro` components instead of relying on Markdown paragraph parsing.

For reusable gameplay cards that should appear in the page table of contents, pass `toc` and optionally `tocDepth`.

```mdx
<KeywordFeatureCard toc tocDepth={2} />
```

The ToC helper in `src/remark-gameplay-card-toc.mjs` can create ToC entries for reusable components. For known reusable components, add a default title to `reusableTocTitles`. For one-off reusable components, you can pass a title from the page:

```mdx
<SomeReusableBlock toc tocTitle="Reusable Section Title" />
```

## Colored Tables

Use a colored table by wrapping a normal Markdown table in a `<div>` with a table color class.

```mdx
<div class="green-table">

| Level | XP To Level | Grit |
|:-----:|:-----------:|:----:|
| 1 | 0 | 1d4 |
| 10 | 450,000 | 9d4 + 1 |

</div>
```

Keep the blank lines between the `<div>` and the table. This helps MDX parse the Markdown table correctly.

Available table classes:

- Original: `red-table`, `blue-table`, `green-table`, `orange-table`, `yellow-table`, `gold-table`, `indigo-table`, `teal-table`, `violet-table`, `purple-table`, `pink-table`, `grey-table`, `black-table`, `brown-table`, and `azure-table`
- High Contrast: `crimson-table`, `royal-blue-table`, and `forest-green-table`
- Pastel: `dusty-rose-table`, `powder-blue-table`, and `sage-green-table`
- Modern: `coral-table`, `cobalt-table`, and `mint-table`
- Fantasy: `dragon-gold-table`, `arcane-violet-table`, and `fey-teal-table`
- Cool: `glacier-blue-table`, `periwinkle-table`, and `deep-teal-table`
- Warm: `ember-table`, `amber-table`, and `terracotta-table`
- Easter Pastel: `easter-pink-table`, `robin-egg-table`, and `easter-lilac-table`

The groups are suggested combinations, not restrictions. You can use any color independently or mix colors from different groups.

Table colors are defined in `src/styles/custom.css`. To add a new color such as `azure-table`, add it to the shared table selector list, then define both light-mode and optional dark-mode CSS variables.

```css
.azure-table {
  --itdatd-table-border: #7dd3fc;
  --itdatd-table-header: #e0f2fe;
  --itdatd-table-header-text: #0c4a6e;
  --itdatd-table-row: #f7fcff;
  --itdatd-table-row-alt: #eef9ff;
  --itdatd-table-hover: #dff4ff;
}
```

## Spell Slot Tables

`SpellSlotTable` renders spell slot data from `src/content/data/spelldata/spell_slots/spell_slots.json`.

```mdx
import SpellSlotTable from '../../../../components/SpellSlotTable.astro';

<SpellSlotTable rank="A" colorTheme="blue-table" />
```

The `rank` prop chooses which spell slot progression to use:

- `A`
- `B`
- `C`
- `D`
- `E`

The `colorTheme` prop uses the same color classes as normal colored tables. Because `SpellSlotTable` renders its generated table inside the same wrapper pattern, changes to the shared colored table CSS also affect spell slot tables. `WeaponTable` accepts the same table color names.

Spell slot tables include cantrip `Preparations` and `Casts` columns before leveled spell slots. The table header automatically groups those columns under `Cantrips` and groups `Level 1`, `Level 2`, and later spell slot columns under `Spell Slots`.

### Bolding Rows And Columns

Use `boldHeader` to bold the header bar.

```mdx
<SpellSlotTable rank="A" colorTheme="blue-table" boldHeader />
```

Use `boldColumn` or `boldColumns` to bold one or more columns. Column numbers are 1-based, so column `1` is `Class Level`.

```mdx
<SpellSlotTable rank="A" colorTheme="blue-table" boldColumn={1} />
```

Use `boldRow` or `boldRows` to bold one or more body rows. Row numbers are 1-based and do not include the header.

```mdx
<SpellSlotTable rank="A" colorTheme="blue-table" boldRows={[1, 5]} />
```

You can combine them:

```mdx
<SpellSlotTable
  rank="A"
  colorTheme="blue-table"
  boldHeader
  boldColumn={1}
/>
```

Live example:

<SpellSlotTable rank="A" colorTheme="blue-table" boldHeader boldColumn={1} />

The table components accept any color-theme class string, so adding another named table theme does not require changing their prop types.

### Card Colors

Set the accent color with the `color` prop:

```mdx
<GameplayCard color="green" title="Class Gameplay">
  Write the card text here.
</GameplayCard>
```

#### Color Set Shortcuts

Use `colorSet` when a GameplayCard should use one of the standard three-color combinations. The shortcut sets the outer card, FeatureSection, and FeatureSubsection colors together.

```mdx
<GameplayCard colorSet="gameplayfeature" title="Requirements and Requisites">
  ...
</GameplayCard>
```

Available shortcuts:

| `colorSet` | Card | Section | Subsection |
|:--|:--|:--|:--|
| `gameplayfeature` | `cobalt` | `mint` | `coral` |
| `proficiencies` | `forest-green` | `royal-blue` | `crimson` |
| `spellcasting` | `arcane-violet` | `fey-teal` | `dragon-gold` |
| `choicefeature` | `easter-lilac` | `robin-egg` | `easter-pink` |
| `fixedfeature` | `powder-blue` | `sage-green` | `dusty-rose` |
| `characterfeature` | `amber` | `terracotta` | `ember` |

Hyphens and spaces in shortcut names are ignored. `classfeature` is also accepted as an alias for `gameplayfeature`; the longer `classfeaturewithchoices` and `classfeaturewithoutchoices` aliases map to `choicefeature` and `fixedfeature`.

Individual color props override their part of a set:

```mdx
<GameplayCard
  colorSet="spellcasting"
  subsectionColor="amber"
  title="Special Spellcasting"
>
  ...
</GameplayCard>
```

Common colors:

- `green`: class or summary cards
- `purple`: feature cards
- `blue`: subclass cards
- `indigo`: ancestry cards
- `yellow`: archetype cards
- `gold`: warm section or subsection accents

Other defined colors:

- `red`
- `orange`
- `teal`
- `violet`
- `grey`
- `black`
- `brown`
- `azure`
- `pink`

Extended palette:

| Suggested Set | GameplayCard, FeatureSection, or FeatureSubsection `color` values |
|:--|:--|
| High Contrast | `crimson`, `royal-blue`, `forest-green` |
| Pastel | `dusty-rose`, `powder-blue`, `sage-green` |
| Modern | `coral`, `cobalt`, `mint` |
| Fantasy | `dragon-gold`, `arcane-violet`, `fey-teal` |
| Cool | `glacier-blue`, `periwinkle`, `deep-teal` |
| Warm | `ember`, `amber`, `terracotta` |
| Easter Pastel | `easter-pink`, `robin-egg`, `easter-lilac` |

Every extended color has a dark-mode value. The matching table class is the color name plus `-table`; for example, `color="dragon-gold"` pairs with `class="dragon-gold-table"`.

```mdx
<GameplayCard
  color="easter-pink"
  sectionColor="robin-egg"
  subsectionColor="easter-lilac"
  title="Easter Pastel Example"
>
  <FeatureSection title="Main Feature">
    <FeatureSubsection title="Nested Feature">
      Each level can use a different color from the trio.
    </FeatureSubsection>
  </FeatureSection>
</GameplayCard>
```

For the matching table treatment:

```mdx
<div class="easter-pink-table">

| Feature | Effect |
|:--|:--|
| Spring Step | Move through difficult terrain. |
| Painted Ward | Gain a bonus against magic. |

</div>
```

All card, section, and subsection colors are defined together at the top of `src/styles/custom.css`:

```css
:root {
  --itdatd-color-green: #22c55e;
  --itdatd-color-gold: #d6a725;
  --itdatd-color-purple: #a855f7;
}
```

Editing one of these variables changes that named color everywhere it is used. Optional dark-mode overrides live in the `:root[data-theme="dark"]` block immediately below the main palette.

To add a new named color, define its palette variable and add it to the corresponding card, section, and subsection color selectors in `src/styles/custom.css`.

```css
.gameplay-card--teal {
  --gameplay-card-accent: var(--itdatd-color-teal);
}
```

Then use it:

```mdx
<GameplayCard color="teal" title="New Card Color">
  Write the card text here.
</GameplayCard>
```

### Header Fields

Gameplay cards support these header fields:

- `eyebrow`
- `subeyebrow`
- `title`
- `subtitle`

By default, cards render:

```txt
eyebrow
title
subtitle
```

Use `headerOrder` when you want a different order.

```mdx
<GameplayCard
  color="purple"
  title="Spellcasting"
  subeyebrow="1st Level Magic-User Feature"
  headerOrder={['title', 'subeyebrow']}
>
  Write the feature text here.
</GameplayCard>
```

### Cards In The Table Of Contents

Add `toc` to make a card title appear in the right-side table of contents.

```mdx
<GameplayCard
  color="purple"
  title="Spellcasting"
  toc
>
  Write the feature text here.
</GameplayCard>
```

The `toc` prop only works when `title` is a quoted string, like `title="Spellcasting"`.

By default, `toc` entries are added as level-three headings. Use `tocDepth={2}` when a card should appear as a higher-level section.

```mdx
<GameplayCard
  color="green"
  title="Magic-User Gameplay"
  toc
  tocDepth={2}
>
  Write the class gameplay overview here.
</GameplayCard>
```

### Feature Sections and Nested Subsections

Use `FeatureSection` inside a card when the rule needs separate titled blocks.

The `title` and optional `label` are always written by you. The component does not generate section names or step numbers.

#### Complete Example

```mdx
<GameplayCard
  color="blue"
  sectionColor="green"
  subsectionColor="gold"
  title="Feature Name"
>
  <FeatureSection title="The Traveller" label="Contemplation">
    Increase your base Move Speed by +5 feet.

    <FeatureSubsection title="Invocation">
      This movement does not provoke Opportunity Actions.
    </FeatureSubsection>
  </FeatureSection>

  <FeatureSection title="Second Section" color="azure" subsectionColor="pink">
    Write the second rule section here.
  </FeatureSection>
</GameplayCard>
```

#### Color Controls

Colors can be set once for the entire card or overridden for one section.

| Component | Prop | Controls | Fallback |
|:--|:--|:--|:--|
| `GameplayCard` | `color` | Outer card sidebar | `purple` |
| `GameplayCard` | `sectionColor` | Every main section sidebar in the card | The card's `color` |
| `GameplayCard` | `subsectionColor` | Every nested subsection sidebar in the card | `--itdatd-feature-subsection` |
| `FeatureSection` | `color` | This main section sidebar only | The card's `sectionColor` |
| `FeatureSection` | `subsectionColor` | Nested subsections inside this section | The card's `subsectionColor` |
| `FeatureSection` | `compact` | Reduces the gap between its title and body content | `false` |
| `FeatureSubsection` | `color` | This nested subsection only | The nearest subsection color |

Card-wide colors:

```mdx
<GameplayCard
  color="purple"
  sectionColor="green"
  subsectionColor="azure"
  title="The Inner Journey"
>
  ...
</GameplayCard>
```

Individual overrides:

```mdx
<FeatureSection
  title="Contemplation of The Traveller"
  color="teal"
  subsectionColor="gold"
>
  The main effect uses a teal sidebar.

  <FeatureSubsection title="Invocation" color="pink">
    This one Invocation overrides the gold subsection color with pink.
  </FeatureSubsection>
</FeatureSection>
```

In short:

- `GameplayCard sectionColor` sets the default sidebar color for every `FeatureSection` in that card.
- `GameplayCard subsectionColor` sets the default nested sidebar color.
- `FeatureSection color` overrides the main sidebar for that one section.
- `FeatureSection subsectionColor` overrides nested subsections within that one section.
- `FeatureSubsection color` overrides a single nested subsection.

If `sectionColor` is omitted, sections inherit the GameplayCard's main `color`. If `subsectionColor` is omitted, nested sections use `--itdatd-feature-subsection` from the shared palette.

Use `compact` for tightly related title-and-body combinations such as an Order name followed immediately by its motto. The reusable Order organization components already enable this automatically.

```mdx
<FeatureSection title="Brotherhood of the Ashen Cross" compact>
  *Mercy through sacrifice*
</FeatureSection>
```

#### Titles and Labels

Use `title` for the actual section heading. Use `label` only when you want a smaller category or step above the title.

```mdx
<FeatureSection title="Spell Preparation">
  Only the title appears.
</FeatureSection>

<FeatureSection title="The Traveller" label="Contemplation">
  The small word “Contemplation” appears above “The Traveller.”
</FeatureSection>
```

Both values are optional and entirely controlled in the MDX. The component never adds labels such as “Step 1,” “Resolution,” or “Contemplation” automatically.

`FeatureSubsection` works the same way:

```mdx
<FeatureSubsection title="Invocation">
  Write the Invocation rules here.
</FeatureSubsection>
```

You can use any title—not only `Invocation`—for example `Valid Creatures`, `Special Case`, or `At Higher Levels`.

#### Markdown h6 Compatibility

For existing Markdown content, a level-six heading (`###### Invocation`) also receives the nested subsection styling. Prefer `FeatureSubsection` when you want explicit title, label, or color control.

```mdx
###### Invocation

This content is indented beneath the Invocation heading.
```

#### Order Feature Cards

`OrderFeatureCard` accepts `colorSet`, `color`, `sectionColor`, and `subsectionColor` and passes them to its underlying GameplayCard.

```mdx
<OrderFeatureCard
  className="Cleric"
  traditions={['Military', 'Devotional']}
  colorSet="choicefeature"
  toc
>
  ...
</OrderFeatureCard>
```

Order traditions use the same indented subsection geometry as `FeatureSubsection`: the sidebar continues beside both the tradition heading and its rules text, with a divider between them and no additional nested-card background.

Military, Devotional, and Stewardship traditions retain their semantic colors:

- Military uses `--itdatd-color-red`.
- Devotional uses `--itdatd-color-violet`.
- Stewardship uses `--itdatd-color-green`.

The reusable Order organization components also accept an optional `traditionColor`. Use it when the surrounding Order is acting as a standardized choice feature and its nested traditions should share that category's subfeature color. If omitted, the semantic Military, Devotional, and Stewardship colors above remain unchanged.

```mdx
<AshenCrossBrotherhood
  include={['Military', 'Devotional']}
  traditionColor="easter-pink"
/>
```

The displayed tradition label, tradition name, and feature name remain controlled by the `tradition`, `title`, and `featureTitle` props on `OrderTradition`.

## Spell Lists

Use `SpellList` to render filtered spell cards from the `data` collection.

```mdx
import { getCollection } from "astro:content";
import SpellList from "../../../../components/SpellList.astro";

export const allEntries = await getCollection("data");

<SpellList
  entries={allEntries}
  datatype="spell"
  level={1}
  className="Cleric"
  sortBy="title"
  sortDir="asc"
  showReverse
  showHeading={false}
  displayFields={['casting', 'shortDescription']}
/>
```

Useful filters:

- `datatype="spell"`
- `level={0}`
- `className="Magic-User"`
- `tag="some-tag"`

Useful list options:

- `showHeading={false}` hides the list's own heading.
- `sortBy="title"` sorts cards by their displayed titles.
- `sortDir="asc"` or `sortDir="desc"` controls sort direction.
- `showReverse` creates a separate card for each reverse spell form.

Useful display fields:

- `level`
- `casting`
- `school`
- `classes`
- `excerpt`
- `shortDescription`

When `classes` is displayed, class names are sorted alphabetically and comma-separated, regardless of their order in spell frontmatter.

### Showing Reverse Spells in a List

`showReverse` is opt-in. Without it, a reversible spell produces only its primary card. With it, the primary and reverse forms appear as separate alphabetized cards:

- **Bless** uses `title` and `shortDescription`, displays `Reverse: Curse`, and links to the top of the shared page.
- **Curse** uses `reverseTitle` and `reverseShortDescription`, displays `Reverse of: Bless`, and links directly to the Curse entry.

Both cards use the primary spell's level and class filters. The reverse card is generated for the list and does not create a second content file or route.

## Full Spell Pages

Full spell pages are rendered by `src/pages/data/[...slug].astro`.

That page:

- creates one route for each `data` collection entry
- uses the primary `title` as the page title
- shows the primary `shortDescription` and, when applicable, a `Reverse form` link in the page introduction
- shows spell metadata in a responsive grid
- sorts displayed class arrays alphabetically
- renders the spell's MDX rules below the metadata block
- passes inherited or overridden metadata to the reverse spell entry

The page title, introduction, and top metadata grid serve as the primary spell's complete header. The primary `SpellEntry` therefore renders only its rules sections. A reverse `SpellEntry` renders its own label, title, description, metadata, and rules so direct links remain self-contained.

Current full-page field order:

1. Spell Level
2. Casting
3. Range
4. Duration
5. Classes

To add a new full-page field, update the schema in `src/content.config.ts`, then render it in `src/pages/data/[...slug].astro`.

## Spell Entry Layout

Use `SpellEntry` to group each spell form's rules. Put `FeatureSection` components inside it for the effect, improvements, components, or other sections.

Spell entries use the same hierarchy as GameplayCards. Every major spell `FeatureSection`, including the first Spell Effect section, receives a top divider so all rules sections begin consistently. A major section has one continuous sidebar beside both its title and content. `FeatureSubsection` blocks are inset beneath it with their own thinner sidebar that continues beside both the subsection title and all of its rules. Primary spell sections use gold with azure subsections; reverse spell sections use violet with pink subsections.

Use `FeatureSubsection` rather than a Markdown level-six heading for spell improvements, valid-creature rules, launching instructions, and similar nested blocks. This ensures the colored bar ends with that subsection's content and the next subsection begins with its own bar.

```mdx
<FeatureSection title="Spell Improvements">
  <FeatureSubsection title="When you can cast 3rd-level spells">
    Write the 3rd-level improvement here.
  </FeatureSubsection>

  <FeatureSubsection title="When you can cast 5th-level spells">
    Write the 5th-level improvement here.
  </FeatureSubsection>
</FeatureSection>
```

Reverse forms begin after a larger vertical break and a full-width reverse-color divider. Their title block also has a reverse-color edge and lightly tinted background. This creates a clear hierarchy of **spell form → major rules section → subsection** without turning each form into another nested card.

### Changing Spell Colors

The four spell hierarchy colors are grouped at the top of `src/styles/custom.css`. Edit only these variables to retheme every spell entry:

```css
:root {
  --itdatd-spell-primary-section: var(--itdatd-color-gold);
  --itdatd-spell-primary-subsection: var(--itdatd-color-azure);
  --itdatd-spell-reverse-section: var(--itdatd-color-violet);
  --itdatd-spell-reverse-subsection: var(--itdatd-color-pink);
}
```

You can point these aliases at any shared palette color, or replace them with direct color values. If light and dark mode should use different colors, repeat the aliases with new values inside the existing `:root[data-theme="dark"]` block.

### Spell Without a Reverse

```mdx
import FeatureSection from '../../../../../components/FeatureSection.astro';
import SpellEntry from '../../../../../components/SpellEntry.astro';

<SpellEntry title="Magic Missile">
  <FeatureSection title="Spell Effect">
    Write the spell effect here.
  </FeatureSection>

  <FeatureSection title="Spell Improvements">
    Write the spell's scaling here.
  </FeatureSection>

  <FeatureSection title="Components">
    Write the spell components here.
  </FeatureSection>
</SpellEntry>
```

The page header displays Magic Missile's title, short description, and metadata. Its primary `SpellEntry` begins directly with the rules, avoiding a repeated `Spell / Magic Missile` heading. `SpellEntry` still creates a lowercase anchor from its title; for example, Magic Missile receives `#magic-missile`.

### Primary and Reverse Entries

Keep the primary and reverse forms in the same MDX file, but give each form its own `SpellEntry` and rule sections. Their effects, improvements, and components can then change independently.

```mdx
import FeatureSection from '../../../../../components/FeatureSection.astro';
import SpellEntry from '../../../../../components/SpellEntry.astro';

<SpellEntry title="Bless">
  <FeatureSection title="Spell Effect">
    Write the Bless effect here.
  </FeatureSection>

  <FeatureSection title="Spell Improvements">
    Write the Bless improvements here.
  </FeatureSection>

  <FeatureSection title="Components">
    Write the Bless components here.
  </FeatureSection>
</SpellEntry>

<SpellEntry
  title="Curse"
  summary="Afflicts foes with divine condemnation."
  variant="reverse"
  metadata={props.reverseMetadata}
>
  <FeatureSection title="Spell Effect">
    Write the Curse effect here.
  </FeatureSection>

  <FeatureSection title="Spell Improvements">
    Write the Curse improvements here.
  </FeatureSection>

  <FeatureSection title="Components">
    Write the Curse components here.
  </FeatureSection>
</SpellEntry>
```

The page header serves as Bless's entry header and includes a `Reverse form: Curse` link. The detail page supplies `props.reverseMetadata` automatically. Passing it to the reverse `SpellEntry` displays a complete metadata grid when a reader follows that link or clicks the Curse list card.

`SpellEntry` props:

- `title`: required entry title; also creates the default anchor.
- `summary`: optional description shown beneath a reverse entry title; primary descriptions come from frontmatter.
- `variant="reverse"`: marks the entry as the reverse form and applies its distinct accent.
- `label`: optionally replaces the default reverse-entry label.
- `id`: optionally replaces the automatically generated anchor.
- `metadata={props.reverseMetadata}`: displays the resolved reverse metadata grid.

## Spell Frontmatter

Spell files live under `src/content/data/spelldata/spell_list/`. The allowed fields are defined in `src/content.config.ts`.

### Standard Spell Frontmatter

```yaml
---
datatype: spell
title: Snap Spark
level: 0
casting: 1 Master Action; Phase 3
range: 30 feet
duration: Instantaneous
classes:
  - Magic-User
shortDescription: Snapping your fingers, you cause a spark to harm a foe.
---
```

### Reversible Spell Frontmatter

```yaml
---
datatype: spell
title: Bless
shortDescription: Bolsters allies with divine favor.
reverseTitle: Curse
reverseShortDescription: Afflicts foes with divine condemnation.
level: 1
casting: 1 Master Action; Phase 4
range: 30 feet
duration: 1 minute
classes:
  - Cleric
  - Theurge
---
```

Reverse spell fields:

- `reverseTitle`: enables the reverse form and supplies its list-card title.
- `reverseShortDescription`: supplies the reverse form's list-card description.
- `reverseCasting`: optional reverse casting override.
- `reverseRange`: optional reverse range override.
- `reverseDuration`: optional reverse duration override.

Spell level and classes always inherit from the primary form. Casting, range, and duration also inherit by default. Add only the overrides that differ:

```yaml
reverseCasting: 1 Action; Phase 3
reverseRange: 60 feet
reverseDuration: 3 rounds
```

The resolved values appear in the reverse entry's metadata grid. Omitting an override keeps the corresponding primary value.

```

```

When diagnosing stale generated output, clear Astro's generated folders:

```bash
rm -rf .astro dist
```
